# PatternautCore

Device-neutral model layer for Patternaut. Pure Swift value types, no UI or
persistence dependencies, so it builds and tests standalone (`swift test`) and
can be consumed by the macOS app as a local package.

## Layout

- `Model/` — the internal pattern representation
  - `Pattern` → `Track` → `Step`, plus `Note`, `FX`, `Meter`, `PatternMetadata`
  - Fully `Codable`; `Pattern.jsonData()` / `Pattern.decoded(from:)` give stable
    JSON for backup and sharing.
- `Devices/` — device profiles and format constants
  - `TrackerFormat` — constants ported from the official `tracker-lib`
    (`ProjectConstants`, `PatternConstants`).
  - `DeviceModel` / `DeviceProfile` — `.trackerMini` and `.trackerPlus`, both on
    the shared 16-track format. Tracks 9–16 are named "Midi 9"… as the device
    names them, but play samples too (Polyend's own demo projects do).
- `Validation/` — `DeviceProfile.validate(_:)` reports issues without mutating,
  supporting the "validate before export" principle.
- `Export/` — full hardware I/O, verified byte-for-byte against `tracker-lib`:
  - `MTPExporter` / `MTPImporter` — `.mtp` patterns (round-trips both ways).
  - `MTProjectExporter` / `MTProjectImporter` — `.mt` projects (patches known
    fields into the embedded `MTProjectTemplate`; unknown regions preserved).
  - `Instrument` / `PTIExporter` / `PTIImporter` — `.pti` instruments (16-bit
    PCM sample + playback params, envelopes, LFOs, filter, slices, granular).
    `WavFile` reads/writes the PCM and converts other depths and rates.
  - `PatternsMetadata` — the `patterns/patternsMetadata` name table, always
    written at the device's full 256 slots.
  - `ProjectBundleWriter` — writes a loadable `<Project>/project.mt` +
    `patterns/pattern_NN.mtp` + `patterns/patternsMetadata` (+ optional
    `instruments/<slot> <name>.pti`) folder to drop on an SD card. Writing into
    an existing project keeps its `project.mt` as the base, removes stale
    patterns and strips macOS `._` companions.
  - `ProjectBundleReader` — reads such a folder back: patterns, names, track
    names, tempo and instruments with their audio, tolerant of older firmware.
  - `CRC32` utility (not enabled; the device accepts a zero CRC, see below).
- `Generation/` — deterministic, seed-based generators and transforms:
  `SeededGenerator` (SplitMix64), `Euclidean` (Bjorklund), `RhythmGenerator`
  (euclidean + probability), `BeatGenerator` (whole beats in a key),
  `Groove` (swing, humanize), `Transform` (rotate, reverse), `Mutation`
  (subtle to chaotic), and `PatternGenerator.assemble` for device-sized patterns.
- `Editor/` — `PatternEditor` (cursor, navigation, per-step edits, undo/redo),
  `NoteKeyMap` (tracker keyboard→pitch) and `FXKeyMap` (effect entry by device
  symbol). Pure, unit-tested logic; the SwiftUI layer is a thin shell over it.
- `Document/` — `ProjectFile`, the `.patternaut` document format (JSON).
- `MIDI/` — `MIDISequencer`, tested but unused by the app since live MIDI was
  removed; kept as the basis for a MIDI file export.
- `Diagnostics/` — `LogBuffer`, behind the app's log panel.

The macOS app lives in `../App` and depends on this package.

## Verifying `.mtp` export

`MTPExporterTests` compares Swift output against reference `.mtp` files produced
by the official `tracker-lib` writer, stored in `Tests/Fixtures/mtp_vectors.json`
(with `mt_vectors.json`, `pti_vectors.json` and `patternsMetadata.json` beside
it). Each case carries its inputs, so the fixtures can be regenerated by running
them through `polyend/tracker-lib` after an update of that library. The oracle
tests pass `tracker-lib`'s own header values explicitly, because the defaults
here follow the device instead (see below).

Settled on a Tracker+ (firmware 1.9.2), where the two sources disagree:

- The per-track `length` byte is the **last step index** (steps − 1), not the
  step count.
- The device writes `.mtp` headers with signature `KS`, type 2 and the real file
  size; `tracker-lib` writes `PM`, type 0 and 0. The defaults are the device's.
- A zero trailer CRC is accepted, so the exporter keeps writing `0`.

## Design notes

- **Effects are the source of truth.** Velocity, probability, microtiming and
  gate are stored as effect lanes (`FXType`) and surfaced via convenience
  accessors on `Step`. This matches the hardware (2 FX per step) and makes
  export a near-identity mapping. The 2-FX limit is enforced by validation, not
  hidden.
- **The FX catalog is ported 1:1 from `tracker-lib`** (`FXType.catalog`, 43
  entries, indices 0–42). Treat `tracker-lib` as the authoritative source;
  symbols differ from the original Tracker manual 1.7.0.
- **Profiles are versioned** so firmware differences (effect set, format schema)
  can be tracked over time.

## Not yet built

- MIDI file import and export. `MIDISequencer` is the starting point.
- Importing a single `.mtp` or `.mt` on its own; import takes a project folder.

Note: a hardware `.mtp` must carry the full device track count (16) — the
device parser infers track count from file size. `PatternGenerator.assemble`
already fills to the full set, and validation warns otherwise.
